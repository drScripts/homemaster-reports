Helen Reopened Reschedule Flow After Booking Was Finalized

After a booking reschedule was successfully finalized, customer post-confirmation messages (such as reference notes or gratitude) re-triggered reschedule classification, causing Helen to report missing dates and pop an unrelated session picker.

1. Executive Summary

In production, several customers experienced a confusing conversation loop immediately following a finalized booking reschedule. For example, after customer Selina Lim rescheduled her 17 Oct session to 23 Oct at 1:00 PM, she sent a clarifying follow-up message: "Pls be reminded tis date is from rescheduling my 17 Oct session tks". In other cases, customers simply replied "Thanks" or "Thanks!!" (e.g. Irene, Jasmine Yeo).

Instead of acknowledging the comment or thanking the customer, Helen fell into an error loop: she claimed she could not find a 17 Oct session, presented interactive buttons for an unrelated booking (e.g. 19 Sept 9:00 AM) and offered a "Reschedule all" button. This eroded customer trust and reopened pending state for already completed changes.

3. Root Cause Analysis (Upstream to Downstream)

Upstream Classifier (L1 / Intent)

Premature Intent Latching

Moonshot Kimi K3 (production classifier) latched onto keywords like "rescheduling" or historical context, classifying reference notes and post-confirmation closers as active modify_booking requests with action: "reschedule".

Middle Stage (released-source.ts)

In-Place Move Blindness

When looking up released source events, replyForReleasedSource only queried the events table for status IN ('cancelled', 'completed'). Since reschedules update events in-place, the source date was absent from events, causing the lookup to return null.

Downstream Fallthrough (reschedule-flow.ts)

Unrelated Session Fallback

In reschedule-flow.ts line 3658, if (matches.length === 0) assumed an error, emitted confusion copy, and presented an active picker for an unrelated upcoming session (e.g. 19 Sept) with context_hint: "reschedule_pick_event".

5. Implementation Details (Code & Schema First)

Priority Order Enforced

In accordance with Rule 3, the fix was implemented in backend state logic and history resolution first, flow routing second, and prompt guidelines last (conceptual guidance only, no incident tokens).

  • Released Source Event History Lookup (supabase/functions/_shared/reschedule/released-source.ts): Added query against event_history for action = 'rescheduled' bounded by customer booking IDs. When a source date was moved in-place, Helen identifies the destination slot, explains warmly that the session was already rescheduled to the new time, and terminates the turn without opening a picker.
  • Reschedule Flow Fallthrough Guard (supabase/functions/_shared/reschedule-flow.ts): In matches.length === 0, if flow.reschedule_followup indicates a recently finalized move and the turn contains no new target dates, Helen confirms the finalized schedule, clears pending drafts, and avoids presenting unrelated session buttons.
  • Post-Reschedule Closer Normalization (supabase/functions/whatsapp-webhook/flows/intent-reassigners.ts): In handleRescheduleFlowLock, post-reschedule thank yous and acknowledgments without fresh target dates are normalized into casual_chat, safely exiting any active reschedule lock.
  • L1 Prompt Clarification (supabase/functions/_shared/helen-prompt.ts): Clarified in L1_CHANGE_SAFETY and L1_RESCHEDULE_ACTION that customer schedule descriptions, confirmations, or post-change gratitude are schedule descriptions and closers, never new change requests.
  • Timer Type Safety (cancel-reschedule-notify.ts & outcome-claims-check.ts): Corrected timer variables to ReturnType<typeof setTimeout> | undefined, resolving TypeScript compilation errors across edge runtimes.
